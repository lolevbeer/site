# Access control

Payload access rules (collection, global, and field `access`) are the single source of truth for who may read or write what. Every Payload Local API call states the identity it runs as:

- **Acting for a person** (anonymous visitor, admin editor, Slack user): `overrideAccess: false` plus their `user` or the hook's `req`. Public pages pass no user — anonymous is the correct identity. Inside hooks, always pass `req` so the call runs as the editor and inside the save transaction.
- **User-less system code** (migrations, `scripts/`, the Untappd and Google hours jobs and their cron, public form intake, rate limiting, Slack notify, and derived-data helpers such as review sync, unique slug/recipe checks, and page revalidation): `overrideAccess: true`. It is allowed only in the files listed as `SYSTEM_OVERRIDE_FILES` in `eslint.config.mjs`, or behind `// eslint-disable-next-line no-restricted-syntax -- system: <reason>` on the `overrideAccess` line.

Never omit `overrideAccess`: Payload 3 defaults an omitted (or `undefined`) flag to `true`, Payload 4 flips it to `false`. ESLint rejects both an omitted flag and an unfenced `true`.

When following access hides something a role legitimately needs, widen that role's access rule rather than bypassing it. A denied relationship populates as a bare ID and our consumers drop non-objects, so access gaps show up as missing content, not errors — check the rendered page.

Current rules worth knowing: beer managers, bartenders, and lead bartenders read every beer; everyone else reads published beers only (drafts never show on the public site, even on a published menu or Coming Soon); admins, event managers, bartenders, and lead bartenders read every event and recurring event (private ones included; contact fields stay event-manager only; the staff-notes `description` is signed-in only, while `summary` is the public event-page copy), everyone else public events only; beer version history is beer-manager only; menu version history follows menu `read` (bartenders see their assigned locations' revisions, other signed-in roles only published ones) and is never public. Every signed-in user reads other users' names and emails, while roles, locations, and Slack IDs stay admin-or-self; beers and menus stamp the last signed-in editor in `updatedBy` ("Last edited by", signed-in readers only); saves with no signed-in user, such as the nightly Untappd sync, keep the previous person. Dashboard widgets (`src/components/admin/*Widget*`, `MenuTargetHistory`, `ScheduleHeatmap`) read as the viewer, and their status buttons PATCH through the REST API as the viewer, so collection `update` access decides who can mark an inquiry contacted, a donation approved or a job application reviewed (admins only for job applications). The "Recurring series" block above the Events list (`RecurringEventsPanel`) also reads as the viewer, so recurring-event `read` decides its rows and `create` its button. The "Recurring food" block above the Food Bookings list (`RecurringFoodPanel`) shows only for `SCHEDULE_READER_ROLES`, the roles the grid it links to loads for; within that, it reads as the viewer, so recurring-food-schedule `read` decides its rows and Food Recurring `update` its button. The draft menu board at `/m/[menuUrl]/preview`, which the admin's live preview pane frames, reads the menu as the signed-in viewer and is a 404 for anonymous visitors; it is the only page allowed inside a same-origin frame (`vercel.json`, `next.config.mjs`). Deletes in the admin go to the trash on beers, menus, events, recurring events, jobs, FAQs, food vendors, stockists and the three inboxes; trashing needs the collection's `delete` access, and `baseAccess.collections.read` (`hideTrashFromVisitors` in `src/access/roles.ts`) keeps trashed documents from signed-out visitors even with `?trash=true`. Uniqueness lookups pass `trash: true`, since a trashed document still holds its unique values. A join field runs on every read of its parent: the Jobs `applications` join follows job-application `read` (admins only), and public job reads pass `joins: false`; do the same for any new join. Query presets on the three inbox lists are stored in Payload's own collection; `queryPresets.access` (`queryPresetAccess` in `src/access/roles.ts`) limits each preset to people who can read the list it filters, on top of the preset's own sharing setting. Scheduled publishes on beers and menus run from `/api/cron/publish-scheduled` (every five minutes, `CRON_SECRET`), which only wakes Payload's `default` job queue; each job saves as the person who scheduled it, under that person's access. Single sign-on (`src/plugins/sso.ts`) gives apps on the `SSO_REDIRECT_URIS` allowlist the signing-in user's own ID, name, email and roles in a 5-minute token that is not a Payload login; the `/api/mcp` endpoint that plugin mounts offers no tools. See `docs/plans/follow-access-control.md` for the migration.

# Caching

Next caps a page at the shortest `revalidate` of any cached read it makes, whatever the page exports, and the root layout's reads are on every page. Keep reads that carry cache tags at an hourly fallback; saves refresh them through the tags. That includes the event and food reads: they depend on the clock only by the Pittsburgh day, which is in their cache key. `tests/int/cache-lifetimes.int.spec.ts` guards this. A dynamic route only gets ISR with `generateStaticParams` (an empty array is enough); without it, `revalidate` does nothing and the route renders per request. `.next/prerender-manifest.json` shows what each route really got.

Every public page also carries the `locations` tag through the root layout, so a location save invalidates the whole site. A save that only affects `/m` boards sets `context.kioskOnly` (see the revalidation plugin). Links rendered in lists, and links to heavy pages, use `prefetch={false}`: each stale prefetch regenerates that page on the server.

# 3D scroll tour (homepage)

The top of the homepage is a scroll-driven walk through the Lawrenceville brewery: `components/home/scroll-tour.tsx` wraps the hero and, after `load` plus an idle slot, adds four more stops and a WebGL scene (`components/home/tour-scene.ts`) holding the brewery model and the featured beer's can. The server's HTML is the plain homepage; the tour is added on the client only.

- **The model is not written here.** `lib/hq/lolev-model.js` and `public/3d/hq/*.webp` are generated in `lolevbeer/hq` and copied at one commit by `node scripts/sync-hq-model.mjs <hq checkout> <commit>`; the file's first line names the commit. Never edit the copy. Its types, `lib/hq/lolev-model.d.ts`, are written by hand and change with a re-sync.
- **three.js must match hq's version** (0.187), and loads only through dynamic imports. `tests/int/home-tour-loading.int.spec.ts` fails on a static import of `three`, the scene or the model from the homepage's files.
- **Three levels** (`lib/tour/quality.ts`): `full` on desktops; `lite` on phones and low-memory devices (no mirrors, no area lights, half-size textures); `none` (no tour) without WebGL 2, with reduced motion or Save-Data. An average frame over 40 ms across the first 60 frames drops one level.
- **Stops** are data in `lib/tour/stops.ts`: camera, can position (in the model's feet: x east, y up, z south), copy and link. `lib/tour/pose.ts` turns scroll position into a camera.
- **Texture slots.** The model's lights and shadows leave a material four of a shader's 16 textures at `full`. The can's label has exactly four, and only without its bump map (`bump: false` in `tour-scene.ts`); a material with more maps does not draw, and three.js logs a shader error.
- **The can** is the first of the first four hero beers with generated label textures (`src/app/(frontend)/page.tsx`); with none, there is no tour.
